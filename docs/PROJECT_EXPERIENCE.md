# SlideFlow 项目经历与面试讲解

SlideFlow 面向 AI 应用开发与 Python 后端岗位，适合展示从模型调用到异步任务、进度恢复和文件导出的工程链路。本次个人实践集中在本地集成验证、SSE 可靠性修复、验证工具与技术文档整理。

## 可直接使用的项目描述

**SlideFlow AI 演示文稿生成平台**

技术栈：Python、FastAPI、LangChain、LangGraph、ARQ、Redis、PostgreSQL、python-pptx、React、TypeScript。

项目简介：面向技术汇报与内容创作，将主题、文本及文档转化为可编辑 PPT。围绕既有实现完成后端集成与可靠性改进，验证材料输入、大纲确认、并发生成、在线编辑和 PPTX 导出的完整流程。

- 完成 FastAPI API、ARQ Worker、PostgreSQL、Redis 与 React 前端的本地集成，验证任务入队、单份 PPT 页级并发、SSE 进度反馈和页面编辑链路；本地单次 5 页生成任务执行耗时 30.83 秒。
- 复现并修复 SSE 快照读取与通道订阅之间的完成事件丢失窗口，调整为先订阅后读取快照，补充终态收尾及订阅资源释放，新增 3 个回归用例验证。
- 补充 Windows 开发脚本和真实模型冒烟脚本，覆盖健康检查、生成状态、SSE 事件、过期 revision 拒绝及 PPTX 导出，整理独立测试数据库和 Redis 逻辑库的运行方式。
- 验证包含既有测试和新增用例的 383 项后端测试，以及 8 组固定语料与主题的 PPTX 导出回归，记录实际页面溢出、卡片布局和质量告警问题，形成可复查的运行基线。

30.83 秒来自单次本地任务执行日志；383 项是当前测试套件总数；8 组是固定语料渲染回归，不表示真实模型生成成功率。

## 一分钟介绍

> 我做的是 SlideFlow 的本地集成与工程化实践，关注 AI 生成任务怎样稳定地进入可编辑文档流程。系统先根据材料生成大纲，用户确认后，API 把生成任务交给 ARQ Worker；Worker 内部按页并发生成，Redis 和 SSE 将进度反馈到前端，最终通过质量检查导出原生 PPTX。
>
> 我这次重点验证了完整运行链路，并复现了 SSE 在读取快照后、订阅消息前可能漏掉完成事件的问题。我调整了顺序和终态处理，补了三个回归用例。另外增加了本地开发和冒烟验证工具。真实试验中，5 页生成任务约 31 秒，但初稿仍有溢出和卡片留白问题，所以我把任务完成、结构校验和视觉质量分开评估。

## 面试问题与回答要点

### 为什么需要独立 Worker

模型调用耗时较长。API 接收请求、保存状态并入队后返回 202，Worker 负责耗时操作，使任务执行与 HTTP 连接生命周期分开。代价是需要管理队列、任务状态和失败恢复；只启动 API 时任务不会自动被消费。

### 页级并发发生在哪里

一次 `generate_deck` 队列任务在内部通过 `asyncio.gather` 派发页面，信号量默认允许同时生成 3 页。Worker 同时还可以消费多个任务，因此单任务信号量不等同于模型服务的全局限流。

### LangChain 和 LangGraph 分别负责什么

LangChain LCEL 负责提示词与结构化模型调用，Pydantic 校验返回结构。LangGraph 负责有状态的单页准备、生成、检查与必要时修复；当前修复最多一轮，部分容量和溢出问题保留为 warning。

### SSE 为什么会漏掉完成事件

旧顺序先取快照，再订阅。如果完成事件在两者之间发布，快照还是旧状态，订阅又错过消息，客户端可能一直等待。修复后先建立订阅，再读取快照，并在首帧已是终态时结束连接。快照和订阅可能产生重复状态，前端按完整状态更新界面。

### 如何证明 PPTX 具有原生编辑能力

后端用 python-pptx 按块构造文本、表格和图表等对象，导出后回读文件检查页数、画布、对象和内容。固定语料验证通过；人工业务试验已确认下载成功。进一步验收应在 Office 软件中逐项修改并保存，检查实际字体和布局表现。

### 生成完成为什么仍然不好看

任务状态和结构 schema 只能验证流程及结构条件。长句列表、信息重复、卡片高度和占位图仍会影响表达效果。本次第 5 页通过精简内容消除了截图中的重叠，但卡片高度和质量规则仍有改进空间。
